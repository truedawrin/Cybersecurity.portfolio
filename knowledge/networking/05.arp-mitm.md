# 📚 ARP and Man-in-the-Middle Attacks

## 📌 Definition

ARP (Address Resolution Protocol) maps IP addresses to MAC addresses on a local network; ARP spoofing abuses its lack of authentication to insert an attacker between two devices.

## 🧠 Core Concept

Any device on a local network can claim to be any IP address via a fake ARP reply, and other devices will simply believe it — the same trust-without-verification weakness as rogue DHCP, at a lower layer.

## ⚙️ How It Works

Broadcast: "Who has 192.168.1.1? Tell 192.168.1.9"
Reply: "192.168.1.1 is at 00:1a:2b:3c:4d:5e"

**ARP spoofing:** attacker sends forged replies to both the victim ("I am the router") and the router ("I am the victim"), inserting themselves into the traffic path — a classic MITM position enabling passive sniffing, active traffic modification, or SSL stripping attempts.

## 🔐 Cybersecurity Relevance

ARP spoofing only works on the same local network, since ARP broadcasts are never routed across the internet — this is why it's a LAN/WiFi-specific attack. Tools like `arpspoof`, `bettercap`, and `ettercap` automate this process (own-lab use only).

## 💻 Example

```bash
ip neigh show      # view your ARP table
```

## 🧪 Practical Example

Checked local ARP table, identified the router's MAC address, and reasoned through why ARP spoofing can't be performed from outside the local network.

## ⚠️ Common Mistakes

- Confusing ARP spoofing (Layer 2, IP↔MAC) with DNS spoofing (Layer 7, name↔IP) — different layers, similar trust exploit
- Assuming HTTPS alone stops MITM entirely — it stops content reading, not the attacker's positional access to traffic metadata

## 🧠 Key Takeaways

- ARP spoofing and rogue DHCP achieve the same outcome (attacker becomes the middleman) via different layers
- Local network trust assumptions are a recurring theme across multiple protocols, not a single isolated bug

# 📚 Firewalls, Proxies, and VPNs

## 📌 Definition

Three tools for controlling and protecting traffic: firewalls filter by rule, proxies deliberately route traffic through an intermediary, VPNs encrypt traffic end-to-end through a tunnel.

## 🧠 Core Concept

A proxy changes where traffic appears to come from and often operates at the application level; a VPN changes how traffic travels, encrypting it so it's unreadable in transit even if intercepted.

## ⚙️ How It Works

```bash
sudo ufw status              # host-based firewall rules
Get-NetFirewallRule           # Windows equivalent
```

Firewall rules filter primarily on IP/port/protocol (Layer 3/4). A **proxy** (e.g., Burp Suite) sits between client and server, deliberately intercepting and even modifying traffic for inspection. A **VPN** encrypts all traffic in a tunnel so a network-level observer (e.g., an ARP-spoofing attacker on public WiFi) only sees unreadable ciphertext.

## 🔐 Cybersecurity Relevance

Burp Suite's entire function as a proxy makes sense once "proxy = deliberate, controllable middleman" is understood. A VPN doesn't stop ARP spoofing from happening — it makes the intercepted traffic useless to the attacker, since it's already encrypted before leaving the device.

## 💻 Example

Running `sudo ufw status` revealed rules allowing several ports (`6000-7100` range) from "Anywhere" instead of scoped to the local subnet — a real, actionable home-network hardening finding.

## 🧪 Practical Example

Audited real `ufw` firewall rules, identified overly broad "Anywhere" access, and reasoned through scoping a rule to the local subnet only.

## ⚠️ Common Mistakes

- Leaving firewall rules scoped to "Anywhere" when only local-network access is actually needed
- Assuming a proxy automatically implies encryption — it does not, by itself

- [[ARP and Man in the Middle]]
- [[Wireshark]]

## 🧠 Key Takeaways

- Firewalls filter, proxies redirect/inspect, VPNs encrypt — three distinct jobs, often confused
- Least-privilege thinking applies to firewall rules exactly as it does to user permissions
