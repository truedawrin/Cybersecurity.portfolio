## 📌 Overview

Cap is an Easy Linux machine centered on a Python web application called "Security Dashboard." The attack path starts with an IDOR in the scan download feature, leads to credentials leaking in a packet capture, and ends with privilege escalation via a dangerous Linux capability set on Python.

## 🧰 Tools Used

- **Nmap** — port and service enumeration.
- **Wireshark** — packet capture analysis.
- **SSH** — initial access.
- **`getcap`** — capability enumeration.
- **Python 3.8** — privilege escalation vector.

---

## 🔎 Reconnaissance

I started with a standard port scan to see what was exposed.

```
nmap -sC -sV -p- -T4 -Pn <target>
```

Three services came back:

- **21/tcp — FTP** (`vsftpd 3.0.3`)
- **22/tcp — SSH** (`OpenSSH 8.2p1 Ubuntu`)
- **80/tcp — HTTP** (`Gunicorn`)

Gunicorn is a Python WSGI server, so I expected a Python web app — most likely Flask.

Before touching the web app, I checked FTP for anonymous access. It was disabled, so I would need real credentials to use it.

---

## 🔍 Enumeration

Browsing to the web app revealed a simple "Security Dashboard" interface. One of the options was a button labeled **Security Snapshot**. Clicking it triggered a scan and redirected me to a URL shaped like this:

```
/data/1
```

The endpoint returned a `.pcap` file — a packet capture of the scan that had just run. The number at the end was a scan ID.

That was an immediate red flag. Exposing another user's scans by guessing a sequential number is a classic Insecure Direct Object Reference.

I changed the ID to `0` and the app served a different capture. I downloaded it and opened it in Wireshark.

Filtering for FTP traffic surfaced a login session in plaintext:

```
USER nathan
PASS Buck3tH4TF0RM3!
```

FTP does not encrypt anything, so the credentials were sitting readable in the capture. The user was `nathan`.

---

## 💥 Exploitation

I used the credentials to log in over SSH and landed a shell as `nathan`. The user flag was in his home directory.

```
cat /home/nathan/user.txt
```

---

## ⬆️ Privilege Escalation

I ran the usual enumeration for `sudo -l`, SUID binaries, and cron jobs — nothing stood out. Then I checked Linux capabilities.

```
getcap -r / 2>/dev/null
```

One line jumped out:

```
/usr/bin/python3.8 = cap_setuid+ep
```

Python 3.8 had the `cap_setuid` capability. That means the interpreter could change its own user ID — including to root — without any SUID bit involved. Whoever set this up had probably done it for some convenient reason and never considered that it effectively handed a root shell to anyone who could run Python.

Since Python can call directly into the OS, escalating was one line:

```
/usr/bin/python3.8 -c 'import os; os.setuid(0); os.system("/bin/bash")'
```

I was root. The flag was in `/root/root.txt`.

```
cat /root/root.txt
```

## 🏁 Flags

| Flag          | Location                |

| **User Flag** | `/home/nathan/user.txt` |
| **Root Flag** | `/root/root.txt`        |

## 🛡️ Defensive Perspective

Each link in this chain had a straightforward fix.

- **IDOR:** The `/data/<id>` endpoint trusted the user's scan ID without verifying ownership. Sequential IDs plus no authorization equals full disclosure of other users' captures. UUIDs and server-side checks close this.
- **Plaintext FTP:** The credentials in that PCAP were readable because FTP sends everything in the clear. Moving to SFTP or SCP removes the entire class of leak.
- **Credential Reuse:** Nathan's FTP password was also his SSH password. That turned a data disclosure bug into interactive access.
- **Capabilities:** `cap_setuid` on a general-purpose interpreter like Python is functionally equivalent to giving every user on the box root. Capabilities should only be set on purpose-built binaries, and any exception must be justified.
- **Defense in Depth:** Fixing any one of these three issues would have broken the chain. All three had to fail at once for me to reach root.

---

## 🧠 What I Learned

- A suspicious URL parameter is often all you need. `/data/1` exposed the whole attack path.
- Plaintext protocols are active liabilities, not just bad practice. Wireshark turned the FTP session into a credential dump in seconds.
- Credential reuse is what turns a low-severity disclosure into a full compromise.
- `getcap -r /` should be one of the first commands run after gaining a shell. Capabilities are frequently overlooked, and one bad setting can mean trivial root.
- Python with `cap_setuid` is a one-liner root exploit. Reviewers should flag it immediately.

## 📚 Key Takeaways

- Real chains come from calm enumeration, not flashy exploits.
- IDOR is not "low severity" when the data behind it contains credentials.
- Always check capabilities — not just SUID and sudo.
