# 🧪 LAB 3.2 — "Student Grade Auditor"

## 📌 Scenario

You are a junior security automation engineer at a small school district. The IT department has been manually checking student grade outputs from a legacy grading script, but they suspect the script mishandles edge cases — invalid input, negative numbers, scores above 100, and unexpected values. They ask you to build a small auditing tool that processes a batch of student scores, classifies each one using the same grading logic, and produces a clean summary report that flags any suspicious or invalid entries. This is a controlled lab using fictional data — no real student records are involved.

## 🎯 Objective

Investigate how the grading script behaves when given a batch of mixed-validity inputs, then extend it into a small Python auditing tool that:

- Reads a list of student scores from a file.
- Classifies each score using the same `if`/`elif`/`else` grading logic.
- Detects and flags invalid entries (non-numeric, negative, or above 100).
- Writes a structured summary report to a text file.

The goal is to practice **input validation**, **error handling**, and **file I/O** — three skills that appear constantly in real security tools (log parsers, config validators, scanner output processing).

## 🧠 Skills Practiced

- Python `if`/`elif`/`else` branching logic
- `try` / `except ValueError` for input validation
- Reading and writing files with `with open()`
- Looping over collections and dictionaries
- Formatting structured output (report generation)
- Thinking defensively about malformed input

- **OS:** CachyOS (or any Linux with Python 3)

## 💻 Implementation

```python
def classify(score):
    if score < 0:
        return "INVALID (negative score)"
    if score > 100:
        return "INVALID (exceeds maximum)"
    if score >= 90:
        return "Grade A"
    elif score >= 80:
        return "Grade B"
    elif score >= 70:
        return "Grade C"
    elif score >= 60:
        return "Grade D"
    else:
        return "Grade F"

report_lines = []

try:
    with open("scores.txt", "r") as file:
        lines = file.readlines()
except FileNotFoundError:
    print("scores.txt not found.")
    exit()

for line in lines:
    line = line.strip()
    if not line:
        continue
    try:
        score = int(line)
        result = classify(score)
        report_lines.append(f"{score} -> {result}")
    except ValueError:
        report_lines.append(f"{line} -> INVALID (not a number)")

with open("grade_report.txt", "w") as report:
    for entry in report_lines:
        report.write(entry + "\n")

print("Audit complete. See grade_report.txt")
```

## 🔎 Findings

- The original script only checked `score > 100` and never validated negative numbers — a negative score would silently fall through to `Grade F`, which is misleading.
- The original script crashed gracefully on `abc` (thanks to `except ValueError`) but offered no recovery path — it just ended.
- Empty input (`""`) triggered `ValueError` and printed the "stop trolling" message, but the message was informal and not machine-readable.
- Structuring the output as `value -> classification` makes the results easy to parse, grep, or feed into another tool.
- Adding validation _before_ classification prevented invalid inputs from being misclassified as legitimate grades.

## 🛡️ Security Relevance

This lab mirrors real cybersecurity work in several important ways:

- **Input validation** is the first line of defense against injection attacks (SQL injection, command injection, XSS). Any tool that accepts external input must validate it _before_ processing.
- **Graceful error handling** is exactly what a network scanner or log parser needs — if one IP or one log line is malformed, the entire tool must not crash.
- **Report generation** mirrors how vulnerability scanners (Nmap, Nessus, Burp) produce structured output that defenders can review and act on.
- **Flagging anomalies** (negative scores, out-of-range values) is conceptually identical to flagging suspicious login times, impossible travel events, or malformed packets in a SIEM.
- **Defensive programming** — checking for bad input _before_ using it — is the mindset behind every secure application.

This is the same pattern used in:

- Log parsers (fail on one line, continue on the rest)
- Vulnerability scanners (classify each result, flag anomalies)
- Authentication systems (reject malformed credentials before comparing)
- Firewalls (drop malformed packets without crashing)

## 🚧 Limitations

- The tool only handles integer scores — decimal scores (e.g., `87.5`) would be flagged as invalid.
- There is no user input mode — scores must be provided via `scores.txt`.
- No logging of _when_ the audit ran, or _who_ ran it (no timestamps, no audit trail).
- The report format is plain text — no CSV or JSON output for downstream automation.
- Error messages are informative but not standardized (no error codes, no severity levels).
