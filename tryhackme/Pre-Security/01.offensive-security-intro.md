### 💥 Exploitation / Validation

The vulnerability lies in a web application that allows unauthorized fund transfers.

By navigating to the discovered `/bank-transfer` directory, I was able to perform a simulated bank transfer to another account:

* **Send from:** 2276
* **Send to:** 8881
* **Amount:** 2000 USD

This demonstrated a business logic flaw in a safe lab environment.

## 🛡️ Defensive Perspective

* **Detection:** Web server logs would show requests to unusual or sensitive directories like `/bank-transfer`. Monitoring access to administrative or financial endpoints is important.
* **Prevention:** Implement proper authorization checks on all sensitive functions. Users should not be able to perform actions they are not authorized to perform, such as transferring funds from another account.
* **Access Control:** Sensitive functionality should require appropriate authentication and authorization.
* **Attack Surface Reduction:** Unnecessary or sensitive endpoints should not be exposed publicly.

## 🧠 What I Learned

* The fundamental difference between offensive security and malicious hacking.
* How to use Gobuster for directory enumeration.
* The importance of checking for hidden pages and directories in web applications.
* How business logic vulnerabilities can allow unauthorized actions even when there is no traditional software exploit.

## 📚 Key Takeaways

* Offensive security involves legally simulating attacks to find vulnerabilities before malicious actors do.
* Even simple web applications can contain hidden functionality that is not linked in the main navigation.
* Tools like Gobuster are useful for mapping the attack surface of a web application.
* Authorization must be properly implemented for sensitive application functionality.
